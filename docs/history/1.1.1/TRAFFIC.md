# 通信計測 · mikeryan 1.1.1

## 比較対象と条件

添付されていた `mikeryan-1.1.0.zip` を別ディレクトリへ展開し、変更していない旧Repository・RelayPoolと、1.1.1の同じクラスを同じ条件で実行しました。元の `mynostr` の公開リレー利用を計測した結果ではありません。

`tests/fixtures/traffic.json` の署名済み公開テストイベントを使用し、実装の `Repository → RelayPool → RelayConnection` を通して模擬WebSocketの実JSONフレームを数えています。本番のイベントID・BIP-340署名検証を有効にしています。リレー側は新しい順・フィルタごとの件数制限を実装しています。

2リレーで同一の完全なデータを返し、ログインしたまま各30投稿のページを5回取得します。ログアウトなしの連続操作と、別に開始する匿名セッションを分けて計測します。ログイン済みの操作では各投稿に自分の正のリアクションを1件ずつ用意しています。リレー間のプロフィール差異・欠落・内部件数制限はこの典型ケースに含めず、別の単体テストで検証しています。速度ではなく件数・JSONバイトの比較なので、試験内の待機間隔は0です。

## 1リレー当たりのREQ数

| 操作 | 1.1.0 | 1.1.1 | kind 0の取得対象人数（旧→新） |
| --- | ---: | ---: | ---: |
| 初回：未知の30人、ログイン済み | 3 | 2 | 30→30 |
| 次ページ：同じ30人・別の投稿、ログイン済み | 3 | 2 | 30→0 |
| 次ページ：既知20人＋未知10人、ログイン済み | 3 | 2 | 30→10 |
| 別画面から戻る：既知の30人、ログイン済み | 3 | 2 | 30→0 |
| 同じページを再取得：既知の30人、ログイン継続 | 3 | 2 | 30→0 |

別に開始した匿名セッションも計測しています。匿名の初回は1リレー当たり旧3REQ→新2REQ、同じ30人の次ページは旧3REQ→新1REQです。これは下のログイン済み5操作の合計には含めません。実UIでログアウトした場合はセッション目録を消すため、その直後は未知プロフィールとして再取得します。

初回はプロフィールの受信数自体を削りません。必要な30人の情報を保ったまま、30個のプロフィールフィルタと1個のいいねフィルタで分割されていた要求を、1個のプロフィールフィルタ＋1個のいいねフィルタへまとめています。既知の人が再登場するページではプロフィールの要求・受信を省きます。

## 5操作・2リレーの合計

| 指標 | 1.1.0 | 1.1.1 | 削減率 |
| --- | ---: | ---: | ---: |
| REQフレーム | 30 | 20 | 33.33% |
| CLOSEフレーム | 30 | 20 | 33.33% |
| フィルタ数 | 320 | 24 | 92.50% |
| 送信JSONバイト（REQ/CLOSE） | 53,354 | 27,682 | 48.12% |
| 受信JSONバイト（EVENT/EOSE） | 423,672 | 318,512 | 24.82% |
| 受信イベント数（各リレーからの受信を合算） | 900 | 680 | 24.44% |

数値は `traffic-results.json` に機械可読形式で保存しています。送信するsubscription IDの文字数もJSONに含むため、操作順と回数も合わせています。接続数は両方2です。全REQに対応するCLOSEを確認しています。

## 数値に含まないもの

TCP・TLS・WebSocketのフレーム/ハンドシェイク、NIP-05のHTTP検証、画像、アカウント初期取得、投稿・署名、公開リレーのCPU・ストレージI/O・実遅延は測定していません。フィルタ数が92.50%減ったことを、サーバーCPUが92.50%減った意味には読み替えられません。

「上に読み込む」の期間探索、同秒の境界拡張、投稿者条件の分割、リレーのプロフィール欠落・旧版混入・件数上限時には追加REQが必要です。正常なプロフィール応答が全部そろう通常ページでの2REQを、すべての操作の上限とは扱いません。ブロックされないことを保証する結果でもありません。

## 不足時の補完

一部しかプロフィールを返さなかったリレーだけで、未取得の人を1人1フィルタ・limit 1で再照会します。一度の補完を20フィルタずつへ分割するため、30人中5人しか返らないリレーでは最初の1REQ＋補完2REQになる場合があります。いいねフィルタは再送しません。別のリレーで取得できていても、そのリレーの未取得分に新しいプロフィールがある可能性を残して扱います。

完全な空応答のEOSEには補完を行いません。拒否・通信失敗後に補完はせず、補完途中の拒否でもそのリレーの残り要求を停止します。未取得・不正・不完全な応答は成功済みプロフィールとして再利用しないため、次の手動操作で再確認できます。任意の非準拠リレーから全件を復元できる保証ではありません。

## 再現

```sh
cd mikeryan
npm test
# 現行版のみ。署名検証も有効。
npm run benchmark
# 以前のZIPを別の場所へ展開して比較。
node scripts/benchmark.mjs --baseline /path/to/mikeryan-1.1.0/mikeryan
# 出力先を変更する場合。
node scripts/benchmark.mjs --baseline /path/to/mikeryan-1.1.0/mikeryan --output /tmp/traffic.json
```

旧版は自動ダウンロードしません。既に渡した1.1.0 ZIPを使います。標準出力に操作ごとの表、`docs/traffic-results.json` に全計測値を出力します。

## 仕様上の根拠

- NIP-01の置換可能イベントと複数authors・複数filter: https://github.com/nostr-protocol/nips/blob/master/01.md
- NIP-11のリレー独自のmax_limit等: https://github.com/nostr-protocol/nips/blob/master/11.md

仕様は2026-09-24に参照。kind 0では最新の置換可能イベントを返す規約を利用しますが、リレー実装差のため補完も必要です。NIP-11を各操作前にHTTP取得する処理は追加していません。
