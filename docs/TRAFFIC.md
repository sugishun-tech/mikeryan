# 通信計測 · mikeryan 1.2.0

## 比較対象と方法

変更していない添付版 **1.1.1** と今回の **1.2.0** を比較しました。元のmynostrや公開リレーの負荷を直接比較した結果ではありません。

同じ署名済み30投稿・30投稿者、同じ2リレー、5回の明示取得です。ログイン済みの場合は各投稿に自分の正のkind:7リアクションを1件用意します。両リレーは同じ完全なデータを返します。本番のRepository → RelayPool → RelayConnectionを通し、イベントIDとBIP-340署名検証を有効にして、実際にシリアライズされるREQ/CLOSE・EVENT/EOSEのUTF-8バイトを数えました。相手のWebSocketは模擬実装です。

「5回の再起動」は、各操作でRepository・ProfileCache・RelayPoolを新しく生成し、同じディスクファイルを使う文字列ストレージアダプターだけを引き継ぐ条件です。実ブラウザーのIndexedDB再起動を計測したわけではありません。1.1.1は起動し直すとプロフィールのメモリ再利用が失われ、1.2.0は保存値を読みます。

## 再起動を挟む5操作・2リレーの合計

| 条件 | 指標 | 1.1.1 | 1.2.0 | 削減率 |
| --- | --- | ---: | ---: | ---: |
| ログイン済み | REQ数 | 20 | 20 | 0.00% |
| ログイン済み | 送信JSONバイト | 42,640 | 26,264 | 38.41% |
| ログイン済み | 受信JSONバイト | 423,170 | 308,930 | 27.00% |
| ログイン済み | 受信イベント数 | 900 | 660 | 26.67% |
| ログイン済み | kind:0の取得対象延べ人数（リレー合算） | 300 | 60 | 80.00% |
| 匿名 | REQ数 | 20 | 12 | 40.00% |
| 匿名 | 送信JSONバイト | 21,430 | 4,846 | 77.39% |
| 匿名 | 受信JSONバイト | 272,270 | 157,926 | 42.00% |
| 匿名 | 受信イベント数 | 600 | 360 | 40.00% |
| 匿名 | kind:0の取得対象延べ人数（リレー合算） | 300 | 60 | 80.00% |

**ログイン済みではREQ数は減りません。** 毎回の投稿REQとページ内の自分のいいねREQを残しているためです。kind:0を後者から除外することでフィルタ・送信量・受信量を減らします。匿名の既知プロフィールでは追加REQ全体がなくなるため、REQ数も減ります。

初回取得の費用は両版とも同じです。2回目以降の既知30人は、新版ではkind:0の取得対象が0人、プロフィール受信が0件です。投稿とページ内の自分のいいねは毎回新規取得します。

## 1つのセッションで5操作した場合

| 条件 | REQ（旧→新） | 送信JSON（旧→新） | 受信JSON（旧→新） |
| --- | ---: | ---: | ---: |
| ログイン済み | 20 → 20 | 26,268 → 26,268 | 308,992 → 308,992 |
| 匿名 | 12 → 12 | 4,846 → 4,846 | 157,926 → 157,926 |

この条件のREQ数・JSON量の追加削減は **0%** です。旧版も同一セッション内のプロフィールは再利用していました。永続化で改善するのは主にセッションをまたぐ利用です。各比較のコネクション数は旧新版で一致します。

## NIP-05の別計測

同じ署名済み1人のプロフィールを5つの新しいセッションで表示します。本番のNip05処理へ検証用HTTP応答を与え、HTTP呼び出し数を数えています。旧版は各回1回ずつで合計5回、新版は初回1回だけで合計1回、**80%減** です。保存後4回の再訪部分だけでは1回も検証HTTPを発生させません。上のリレーJSON量の表にこのHTTP回数やバイトを混ぜていません。

## 画面操作の確認

別のChromium画面試験で、ホーム・グローバル・通知・プロフィールの全タブ・スレッドへアクセスしただけではREQ0件であることを確認しました。未取得のプロフィールへの移動、ログイン、再起動相当の独立ページへの保存状態引継ぎでも自動取得しません。取得済みプロフィールを表示してもNIP-05 HTTPは0件です。これはアプリの読取り通信であり、HTML/JS/CSS/default.json/画像の通信が0という意味ではありません。

## 含まないもの・限界

ログインアカウントのフォロー・ミュート初期確認、一覧そのものの大量読み取り、投稿・署名・公開リレー更新、HTML/JS/CSS、プロフィール画像、HTTP応答バイト、TCP/TLS、WebSocketのフレーム/ハンドシェイク、リレーのCPU・ストレージI/O・実遅延・利用料金はこの数値に含めません。CPUが27%下がる、料金が27%安くなるという結果ではありません。

完全なプロフィールが返る条件です。欠落・件数制限・旧版混入・同秒境界・上方向の期間探索・複数の投稿者条件では追加REQがあり得ます。新しい未知ユーザーが多い場合や保存領域が使えない場合は削減が小さくなります。手動の「プロフィールを更新」と安全な書き込み前確認は意図的に再取得します。

実IndexedDB・SharedWorker・Firefox・本番拡張機能・公開リレーは未検証です。保存領域の動作をテスト用アダプターで確認したことを、ネイティブ保存APIの実測に置き換えて説明しません。

## 再現

```sh
cd mikeryan
npm test
node scripts/benchmark-persistence.mjs --baseline /path/to/1.1.1/mikeryan
node scripts/benchmark-persistence.mjs --baseline /path/to/1.1.1/mikeryan --output /tmp/traffic.json
```

旧版は自動取得しません。以前の1.1.1 ZIPを別ディレクトリへ展開して指定します。標準出力に比較、`docs/persistence-traffic-results.json` に操作別の生データが出ます。記載のバイト数には実際のsubscription IDも含みます。
