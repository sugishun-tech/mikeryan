# mikeryan 1.3.0

`mynostr` と `mynostr_profile` を一つの静的サイトに統合したNostrクライアントです。バックエンド、npm installは不要です。Xの埋め込みを表示するときだけ、親画面から隔離したフレームで公式widgetsを読み込みます。

## Nostr参照・画像・動画・リポスト

| 種類 | 表示 |
| --- | --- |
| NIP-21 | note / neventは投稿、npub / nprofileはプロフィール、naddrは指定座標の最新版。残りのURIは通常リンク。 |
| 画像・NIP-92 | 本文のHTTPS画像URLをlazy表示。imetaのMIME・寸法・代替テキストを利用。幅は投稿領域内、高さは最大520px。 |
| X | x.com / twitter.comのstatus URLを隔離フレームで表示。拒否・未取得・CSP等ではリンク。 |
| YouTube | watch / youtu.be / shortsに対応。基本16:9、狭い画面ではプレイヤー最小高さを優先。ほかの動画サイトはリンクのみ。 |
| リポスト・引用 | kind:6 / kind:16のリポスト者と元投稿。元JSONの署名を検証し、JSONが使えない場合はタグから取得。qタグは返信と区別して引用表示。 |

**1投稿あたり、これら全部で最大1件です。** 本文中で最初の対応候補を選びます。NIP-21は最初のURIしか候補にしません。本文候補がない場合は最初のqタグを使用します。失敗した候補を後続候補で置換して通信を連鎖させません。本文リンクを保持し、エラーでも投稿全体を壊しません。

最大埋め込み深度は1です。リポストの元投稿も1枠を消費するため、元投稿内の画像・動画・Nostr参照はリンクになります。同じ外部メディアの重複表示も現在画面ではリンクにします。取得結果は永続化せず、設定外リレーへの自動接続を行いません。

**初期設定の注意:** 受領版の `default.json` には `https` と `nostr\:` の本文ミュートがあり、そのまま維持しています。該当投稿を表示する場合は「設定」の本文ミュートから該当パターンを削除してください。画像は画像表示設定にも従います。非日本語のみ・`#` の既存ミュートも変更していません。

Node **281件**、Chromium **275項目**、localhost実WebSocket **9項目**が通過。Xの本番表示、YouTubeの実再生、公衆リレー、実拡張、ネイティブCSP適用は未検証です。画像・X widgets・YouTube通知は画面試験で模擬しています。YouTubeの通知判定は互換ハンドシェイクであり、公開JavaScript APIを親画面へ読み込む方式ではありません。詳細は [設計](docs/ARCHITECTURE.md)、[検証結果](docs/TEST_RESULTS.md)、[変更履歴](CHANGELOG.md) を参照してください。

## 読み込みはボタン操作だけ

ホーム、グローバル、通知、プロフィール、スレッドへ移動しただけでは投稿を取得しません。ログイン・再読み込み・タブ切り替え・スクロールでも投稿や公開リストを自動取得しません。画面へ戻ると投稿・リストは未取得の状態になります。

| ボタン | 動作 |
| --- | --- |
| 下に読み込む | 画面内の一番下の投稿を基準に、古い側へ最大30件。 |
| 上に読み込む | 画面内の一番上の投稿を基準に、新しい側の近い投稿を最大30件。 |
| 最新を読み込む | 押した時点の現在時刻から古い側へ最大30件。表示を置き換えて先頭へ移動。 |

3ボタンはスクロールに追従し、上下の追加では読んでいる投稿の画面上の位置を維持します。初期状態には「まだ取得していません」と表示します。「さらに読み込む」「いいね同期」「新着確認」や右側の通信状況カードはありません。

プロフィールのフォロー・フォロワー・ミュート・リレーは、それぞれの「○○を取得」で読み込みます。スレッドは「投稿を取得」で本文と返信先を取得し、返信一覧は3ボタンで別に取得します。ホーム等で必要な自分のフォロー・公開ミュートは、初回の読み込みボタン操作に含めて取得します。

30件は1操作で画面へ反映する上限です。表示条件で隠れた分を自動的に追加取得して30件へ埋めません。同秒の境界・上方向の期間探索・複数リレーの重複により、受信イベント総数は30を超える場合があります。上下の探索は1操作最大6回、同秒集中は1フィルタ最大1600件で打ち切ります。各リレー・各フィルタの少件数応答に対する境界確認は、初回REQに最大2回を追加します。全履歴の完全性を保証しません。

## 抜けを防ぐ取得と再試行

投稿・通知は、リレー別・検索条件別に読めた範囲を確認してからページを進めます。遅いリレーのタイムアウトや、非空でも不完全な応答では現在の一覧と取得位置を維持します。少件数応答は古い側を確認し、取得済みの境界より先に未確認部分があるときは飛び越しません。確認できない場合は「未完了」と表示し、同じボタンで再試行します。

フォロー・公開ミュート一覧は署名済みの公開鍵リストを先に表示します。名前や相互フォローの確認が失敗してもユーザー行を消しません。「相互未確認」と「表示中の補助情報を再取得」で未確認状態を区別します。この再取得は失敗・未取得の補助情報を対象とし、既に保存済みのプロフィールを強制更新するものではありません。

フォロワーは各読み取りリレーを独立に検索し、取得できた署名付きの候補を、別リレーの停止で隠しません。加えて本人のフォロー先を1操作につき最大30人ずつ直接確認し、逆引き検索で漏れた相互フォローも補います。検索と直接照会と画面内の既知イベントを比較し、最も新しい署名付きkind:3を判定に使用します。同時刻ならID順で選びます。空応答・古い応答・通信失敗はフォロー解除の証拠にはしません。より新しい署名付きリストから外れていた場合は除外します。

最新状態の照会が未完了でも、受信済みのフォロー証拠がある人は一覧を保持して警告を表示します。証拠自体がない人は未確認の候補として残し、「未確認の候補を再確認」で最大30人ずつ再試行できます。未確認を一律に非フォローとせず、相互関係が不明な行では「相互未確認」と表示します。別人の新しいkind:3を受信した際にも表示中の相互バッジを更新します。フォロワーの順序はリレーごとの発見順を含み、全リレーでの厳密な時系列順ではありません。複数の取得経路が重なっても、一人一行・1操作で新たに表示する人数は最大30人です。

公開リスト（kind:3 / 10000 / 10002）には通常投稿と別の容量上限を使います。4MiB・50,000タグまでを上限とし、超過を正常な空リストとして扱いません。既存のミュート・表示条件、接続先と読み取りリレー数、手動取得・30件上限・プロフィールだけの永続化は変更していません。

取得対象は設定で選択した読み取りリレーです。そこに存在しないデータ、リレー側の削除・保持期間・アクセス制限は復元できません。NIP-01には完全な結果数やIDカーソルがないため、宣言されない上限で最後の同秒群だけが省略される等、完全性を判別できないケースは残ります。全Nostrを自動探索する機能は追加していません。

## プロフィールだけを永続キャッシュ

保存対象は署名済みkind:0イベントです。表示名、ユーザー名、自己紹介、画像・カバーのURL、NIP-05、ウェブサイトなど、未知フィールドも含むプロフィールJSONと元の署名を保持します。画像ファイル本体のダウンロード保存はしません。

通常はIndexedDBのプロフィール専用ストアを使います。利用できない場合はプロフィール専用のlocalStorageキーへ切り替えます。どちらも使えない場合は現在の画面だけ動かし、保存できない旨を表示します。アプリ側の期限切れ・定期再検証・バックグラウンド更新はありません。ブラウザー自身の容量制限・サイトデータ削除まで防ぐものではありません。

取得済みの人は、投稿・通知・ユーザー一覧・プロフィールページ・アカウント表示で同じ保存データを使用します。再読み込み、タブを閉じる、ログアウト、アカウント切り替え、接続先リレーの変更でも再取得しません。メモリの高速参照は最大2000人ですが、そこから外れた人もディスクから読み、通信せず復元します。未取得・不正なプロフィールを取得成功として永続化しません。

**保存済みの人の再取得は、プロフィールページの「プロフィールを更新」で行います。** 投稿取得で初めて登場した未知の人は、必要なメタデータをまとめて取得し保存します。未取得の人のページを直接開いただけでは取得せず、公開鍵と取得ボタンを表示します。プロフィール更新はその人のkind:0だけを対象にし、投稿や公開リストを取得し直しません。

NIP-05検証結果もプロフィールに結び付けて保存します。既知の人を表示・スクロール・再訪しても検証HTTPを繰り返しません。認証マークの説明には保存時の検証結果と日時を表示し、現在も有効である保証と混同しません。通信・CORSで検証できなかった結果も手動更新まで再試行しません。NIP-05検証を無効にしている場合はHTTPを実行しません。

プロフィールを自分で保存する操作では、未知フィールドの消失を防ぐため全設定リレーで最新情報を確認してから署名します。成功した自分のプロフィールはキャッシュにも反映します。未取得のプロフィールを編集する場合は空のフォームで上書きしないため編集ボタン操作時に取得します。これらは閲覧時の自動更新ではなく、明示した書き込みに必要な確認です。

### 保存しないもの

投稿・ページ・他人や自分のフォローリスト・フォロワー候補・ミュートリスト・公開リレーリスト・いいね・完了した問い合わせ結果は永続保存しません。現在表示している画面を組み立てるための一時データは持ちますが、移動後に一覧として復元しません。再び取得ボタンを押すとリレーへ要求します。

設定ページのリレー設定、ログイン公開鍵、下書き、リレー休止情報、署名済みの未完了送信は従来どおり保存します。未完了送信はユーザー自身の書き込みで、取得結果のキャッシュではありません。秘密鍵は保存しません。

## プロフィールの公開リレーを編集

自分のプロフィールの「リレー」タブで「リレーを取得」を押すと公開リストが表示されます。URLと用途（読み書き／読み取り／書き込み）を指定して追加し、各行の「削除」で削除できます。他人のリストは表示のみです。

変更直前に全設定リレーから最新のNIP-65リスト（kind:10002）を読み、追加・削除するURLだけを変更します。他のURL、read/writeの指定、未知タグ、contentは保持します。重複追加は署名・再公開しません。古いkind:3内のリレー情報しかない場合はkind:10002へ移行して公開します。最後のURLの削除も可能です。署名拒否や取得失敗時は入力を残してエラーを表示します。

**これはNostrに公開する自分のリレー情報です。設定ページの接続先リレーとは別です。** 追加・削除してもアプリの接続先設定を書き換えず、追加URLへ勝手に接続しません。署名済みリストは従来どおり設定中のリレーへ送信します。

## 通信設計と計測

取得期間・種類・投稿者・ページ内のIDを絞り、未知のプロフィールをまとめます。ページ内の自分のいいねと同じREQへまとめ、処理中だけ同一要求を共有します。接続共有、要求間隔、EOSE後のCLOSE、拒否時の休止を維持します。不足したプロフィールや公開リストは、当該リレーに限って有限の補完を行います。まとめたフィルタが一部しか処理されない場合は不足者を単独条件で確認し、拒否・タイムアウト後の無限再試行はしません。ページ取得のフィルタはリレーごとに個別処理します。

**以下は1.1.1対1.2.0の保存機能についての過去計測です。1.2.1以降の境界確認・欠落補完による通信増減を計測したものではありません。** 同じ署名済み30投稿・30人・2リレー・5回の取得で比較しました。セッションを毎回作り直すログイン済み条件では受信JSONが27.00%減、送信JSONが38.41%減です。REQ数は20→20で変わりません。匿名の同条件はREQ20→12、受信JSON42.00%減です。1つのセッションを使い続ける場合は旧版もメモリで再利用していたため、この計測では追加の削減はありません。

模擬リレーでのJSONメッセージ計測です。ネイティブIndexedDB・実リレーのCPU・実際の料金を計測した結果ではありません。条件、除外項目、再現方法、NIP-05の別計測は [通信計測](docs/TRAFFIC.md) を参照してください。

## 配置と更新

ZIP内の `mikeryan/` の中身をリポジトリ直下に置き、`index.html` がルートにある状態にします。GitHub Pagesの公開元にはブランチのルート `(root)` を指定します。`docs/` は説明ページで、アプリの公開元ではありません。

今回のZIPは全体版です。同じ位置へまとめて配置し、新しい `js/content/`、`js/ui/embeds.js`、`assets/embeds/` も必ず含めてください。JS/CSS/SharedWorkerの版番号は1.3.0です。独自の `default.json` を残し、ブラウザーのサイトデータは消さないでください。ログイン情報や設定の形式は変更していません。

1.1.1のメモリにしかなかったプロフィールは新しいブラウザー実行へ移せないため、1.2.0で初めて取得したときから保存が始まります。古い1.0系のDBは自動取り込み・自動削除しません。詳しくは [移行](docs/MIGRATION.md) を参照してください。

```sh
cd mikeryan
python3 -m http.server 8000
# http://localhost:8000/ を開く
```

Node.js 20以上がある場合:

```sh
npm run check
npm test
npm run build
```

`dist/` は公開用コピーです。ブランチのルートを公開する場合は `index.html` が公開元の直下にある状態にします。NIP-07拡張機能による署名許可はログイン状態とは別で、拡張機能の承認は迂回しません。
